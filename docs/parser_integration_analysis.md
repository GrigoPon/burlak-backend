# Анализ Интеграции Первой Реализации Парсера в Архитектуру Бэкенда

Этот документ описывает, как интегрировать существующие наработки по парсингу и сопоставлению данных (`burlak_parser`) в новую распределенную архитектуру на базе FastAPI, Celery и SQLite, а также определяет границы применимости эвристического и динамического (ML-driven) парсинга.

---

## 1. Общие Выводы (Суть)

* **Существующий код `burlak_parser` — это ценный фундамент.** Он реализует всю ключевую математику проекта (нечеткое сравнение парт-номеров, нормализацию данных, расчет излишков и дефицитов) и покрыт более чем **850 тестами**.
* **Переход на динамический парсинг (ML-driven):** Архитектура проекта требует полной гибкости (универсальность без привязки к конкретным шаблонам автопроизводителей). Вместо того чтобы на бэкенде пытаться жестко угадать структуру файлов (эвристики), мы делегируем определение координат колонок ML-сервису.
* **Стратегия интеграции:**
  1. Выделить готовую бизнес-логику (нормализаторы и матчеры).
  2. Скопировать эту логику в слой `app/services/` нового бэкенда.
  3. Реализовать простой парсер карт на основе координат из `mapping_config` от ML.
  4. Перевести тесты на новые сервисы.
  5. Убрать из репозитория неиспользуемые компоненты эвристического парсинга для поддержания чистоты кодовой базы.

---

## 2. Какие компоненты `burlak_parser` интегрируются в новую архитектуру

В текущей кодовой базе есть файлы, реализующие ядро бизнес-логики. Их необходимо перенести в структуру `app/services/`:

### А. Модуль нормализации ([burlak_parser/normalizer.py](file:///burlak-backend/burlak_parser/normalizer.py))
Отвечает за очистку и стандартизацию данных:
* `QuantityNormalizer` — обрабатывает количества деталей (дроби, пустые ячейки, тире разных типов, переводя их в `0.0`).
* `PartNumberNormalizer` — очищает каталожные номера от спецсимволов и дефисов, отсеивает невалидные строки (китайские иероглифы, служебный текст, "N/A" и т.д.).
* **Решение:** Копируем этот файл в `app/services/normalizer.py` (с обновлением импортов).

### Б. Нечеткое сопоставление ([burlak_parser/fuzzy_matcher.py](file:///burlak-backend/burlak_parser/fuzzy_matcher.py))
Реализует правила матчинга деталей на производстве:
* Сопоставляет номера с разным написанием (например, `ABCD-123` и `ABCD123` совпадают), но строго запрещает совпадение при отличии в символах (например, `ABCD123` и `ABCD124` — разные детали).
* Класс `FuzzyMatcher` строит быстрый поисковый индекс для сопоставления.
* **Решение:** Копируем этот файл в `app/services/fuzzy_matcher.py`.

### В. Сверка данных и расчет отчетов (`comparator.py`, `report_generator.py`)
* Реализуют сложный расчет расхождений объемов деталей по комплектациям и формирование итогового файла `diff.xlsx`.
* **Решение:** Переносим логику в `app/services/comparison_service.py` для использования в финальной Celery-задаче `aggregate.py`.

## 3. Какие компоненты заменяются на динамическую (ML) логику

Ряд файлов исходного прототипа реализовывал эвристический подход (поиск колонок по ключевым словам в коде Python). В новой архитектуре эти задачи перекладываются на ML-сервис:

| Исходный файл | Что делал (эвристика) | Как будет работать в новой архитектуре |
|---|---|---|
| **`card_parser.py`** | Парсил объединенные ячейки, пытался найти шапку таблицы по ключевым словам. | **Упрощается.** Новый парсер берет готовые координаты колонок из `mapping_config` (от LLM) и читает строки по ним напрямую через `openpyxl`. |
| **`heuristic_analyzer.py`** | Алгоритмически определял типы листов Excel. | **Заменяется на ML.** Модель возвращает типы листов (`bom_data`, `card_data`, `service`) прямо в ответе `/analyze-structure`. |
| **`file_classification_rules`** | Жестко классифицировал файлы в Python. | **Заменяется регулярными выражениями.** ML присылает regex-паттерны в `mapping_config.cards.file_classification_rules`, по которым воркер распределяет файлы. |

## 4. Пошаговый план перехода (Migration Steps)

Для плавного переноса ядра и сохранения всех зеленых тестов разработчикам рекомендуется выполнить следующие шаги:

1. **Создание новых модулей:**
   Создать `app/services/normalizer.py` и `app/services/fuzzy_matcher.py` на основе аналогичных файлов из `burlak_parser`.
2. **Написание ML-парсера:**
   Реализовать `card_parser_service.py` с использованием новых модулей нормализации.
3. **Обновление импортов в тестах:**
   В файлах папки `tests/` заменить старые импорты `burlak_parser` на импорты из `app/services/`.
4. **Запуск тестов:**
   Выполнить `uv run pytest`. Все тесты нормализации, нечеткого сравнения и парсинга должны успешно пройти.
5. **Удаление старой папки:**
   Удалить временную папку `burlak_parser/` для очистки репозитория.
